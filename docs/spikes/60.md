# Spike: #60 — trial AetherEngine as a second playback engine

**Status**: open
**Issue**: https://github.com/axeslasher/Jelly-Shark/issues/60
**Started**: 2026-11-17
**Branch**: `spike/60-aetherengine` (not meant to merge)

This is an adoption trial, not a root-cause hunt, so "Symptom" is replaced by "Question".
The ledger rules from `issue-template.md` still apply: nothing graduates to a doc, issue,
PR, or memory file until it is CONFIRMED here with cited evidence.

## Question

Can AetherEngine 7.70.x sit behind the `PlayerEngine` seam, hosted in the existing
`AVPlayerViewController`, well enough to justify an opt-in engine in Settings?

The trial stops at the first hypothesis that is falsified with no workaround.

## Experiments run

Append-only. Newest last.

### E1 — build with the dependency added (2026-11-17, local builds, Xcode 27.2)

- **Targets**: H1
- **Falsifies H1 if**: a build exits non-zero for a reason inside the dependency.
- **Method**: AetherEngine 7.70.0 (FFmpegBuild 3.15.0, LibDovi 2.2.0, no traits) added to
  `Features/Package.swift`, plus a placeholder file that imports the module.
  `xcodebuild -scheme "Jelly Shark" ... CODE_SIGNING_ALLOWED=NO build`, one per row.
- **Raw output** (exit codes):

```
tvos-device       generic/platform=tvOS, Release                 exit=0
xros-device       generic/platform=visionOS, Release             exit=0
tvos-sim          generic/platform=tvOS Simulator, Debug         exit=65
xros-sim          generic/platform=visionOS Simulator, Debug     exit=65
tvos-sim-arm64    Apple TV 4K (3rd generation) simulator, Debug  exit=0
xros-sim-arm64    Apple Vision Pro simulator, Debug              exit=0
```

- **Why the generic simulator builds failed**: they also link `x86_64`, and the prebuilt
  binaries are arm64-only for the simulator
  (`ld: warning: ignoring file ... AetherLibavcodec: fat file missing arch 'x86_64'`, same for
  `libdovi.a`). An Intel Mac cannot build the simulator target with this dependency. Whether
  CI builds a generic simulator destination has not been checked.
- **Result**: H1 → CONFIRMED for arm64 hosts.

### E2 — added size on Apple TV (2026-11-17, local Release builds, unsigned)

- **Targets**: H2
- **Method**: `main` at fdb7e64 built into one derived-data folder, the spike into another,
  same command. Executables copied and run through `strip -S -x` for the stripped row.
- **Raw output**:

### E3 — trial engine on the simulator fixtures (2026-11-17, tvOS 27 simulator, Jellyfin 10.11.11)

- **Targets**: H3 (simulator half), open question 1
- **Falsifies H3 if**: the playhead does not advance on the HEVC MKV fixture.
- **Method**: `UICheckSpikeAether` (launch argument `-spike-aether`) against
  `UI_CHECK_SPIKE=1 server.sh up 10.11.11 8097`. Sign in, open the title, press Play, read
  the server's session, wait 8 s, read the app log back from the simulator. All runs exit 0.
- **Raw output** (app log, one title shown; the other two match apart from the codec id):

```
[start] "Signal Fire" → directPlay (container=mkv directPlay=true directStream=true ...)
[VTProbe] canHardwareDecode codec=173 640x360 -> false (status=-12906)
[AetherEngine] dispatch: codec=173 → software
[AetherEngine] #321: effective video route = software
[AetherEngine] AE#462: audio delivery = decoded
[aether] playhead 5.2s route=software phase=playing
[report] stopped ok "Signal Fire" pos=89351265
```

| Title | Source | Server play method | Route | Playhead |
|---|---|---|---|---|
| Signal Fire | HEVC HDR10, E-AC-3 5.1 | DirectPlay | software | 5.2 s logged, stop at 8.9 s |
| Copper Wire | H.264, DTS 5.1 | DirectPlay | software | 5.2 s logged, stop at 8.9 s |
| Glass Orbit | AV1, Opus | DirectPlay | software | 5.2 s logged, stop at 8.9 s |

- **Results**:
  1. Open question 1 → answered. Widening the declared capabilities alone made the server
     answer direct play for all three MKVs; `StreamDelivery` is unchanged.
  2. **The simulator cannot reach the engine's native (AVPlayer) route.** VideoToolbox
     reports no hardware decode there even for H.264 (`status=-12906`), so every title goes
     to the software route, and `DecodePath` has no `.native` to force it. H3's native half,
     H5 and H6 are therefore device-only.
  3. The software route does play: a frame of the test pattern at 00:00:08 is on screen in
     `04-playing-later.png`. It needed `AetherPlayerSurface` mounted; with only
     `AVPlayerViewController` the engine logged "the host never bound a render surface" and
     the screen stayed black. That route has no transport controls in this spike.
  4. First run finding, fixed in the adapter: a `play()` that lands while `load` is still
     running is dropped (the clock sat at 0, `[SWHost] paused before the first frame`). The
     view model calls `play()` right after `load`, so the adapter replays it when the load
     returns. Any real conformer needs the same.
  5. Seen in passing, not chased: Jellyfin answered the engine's suffix-range prefetch
     (`bytes=-65536`) with 500; the engine carried on without it.
- **Not evidence of appearance.** The HDR10 frame looks posterised in the simulator
  screenshot. The simulator shows no HDR, so that says nothing about a device.
- **Result**: H3 → still TESTING. Software route confirmed on the simulator; native route
  untested.

## Open questions

1. Does a wider direct-play declaration alone route sessions to the new engine? Read, not
   run: `StreamDeliverySelector.delivery` returns `DirectDelivery` whenever the resolved
   play method is direct play, and the device profile is derived from the engine's
   `capabilities`. So an engine that declares MKV should get the original file's URL with no
   change to `StreamDelivery`. Hypothesis until H3 runs.
2. Simulator fixtures: the sim-ui-check library is H.264/AAC MP4 only, which the default
   engine already direct-plays, so it cannot tell the engines apart. The local ffmpeg can
   make HEVC 10-bit PQ, AV1, DTS, TrueHD, E-AC-3 5.1, SRT, ASS and DVD/DVB bitmap subtitles
   in MKV. It cannot make Dolby Vision (no `dovi_tool`), Atmos (no JOC encoder) or PGS (no
   encoder), so those stay device-only on real library titles.
3. Out of scope until H1 to H6 pass: software-route content (no AVKit player), host-drawn
   subtitles, and the optional TrueHD / DTS:X / profile 7 traits.
